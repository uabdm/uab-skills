# UAB Deploy — push the generated app to GitHub via an MCP connector

This skill's entire job is: take an app that already exists on disk in
this sandbox — generated by `uab-app-creator-nobrand` or a sibling,
possibly branded by `uab-branding`, possibly QA'd by `uab-app-qa` — and
get its files into a dedicated branch of a GitHub repository, creating
that repo first if it doesn't already exist. It never touches Azure
Bicep, `azure.yaml`, or pipeline files, and never runs a build or QA
itself. It is the mirror image of `uab-app-creator-nobrand`'s "this skill
never runs a git command" boundary — this is the one skill in the family
whose entire job *is* getting code into a repository, just never through
`git` itself.

**This skill is invoked directly by the orchestrating process, on its
own, as a distinct step** — never from inside `uab-app-creator-nobrand`,
`uab-app-builder`, `uab-branding`, or `uab-app-qa`'s own instructions.
Those skills are unchanged by this one existing.

**Timing:** this runs automatically, with no approval prompt from this
skill, right before the Daytona sandbox that generated the app tears
down. There is deliberately no "looks good, go ahead" hard-stop here the
way there is before generation in `uab-app-creator-nobrand` — the
decision to push already happened when the orchestrating process chose
to invoke this skill. (TrueForge's own `require_approval_for_tools`
policy can still pause a run on any tool this skill calls — see
"Mechanism" below; that's outside this skill's control.)

## Mechanism: GitHub MCP connector via Code Mode — no git, no token

Full detail in `references/mcp-mechanism.md`. Summary: this skill never
runs `git` and never reads a credential of any kind. It pushes entirely
through a GitHub MCP server connector configured once in TrueForge
(`Settings → Connectors`), called from `scripts/deploy.py` via Code
Mode's bridged `mcp_client.call_tool(server_name, tool_name, body={...})`
— the call runs from inside this sandbox, but the harness applies the
connector's stored credentials on the other end; **the sandbox never
holds the token**. The only thing this skill needs to know is the
connector's *name* (`--mcp-server-name`, default `github`) — not secret,
just an address.

**This mechanism has real unconfirmed details** — exact MCP tool names,
whether the push tool accepts binary content, whether `scripts/deploy.py`
can be run as a checked-in file versus needing its source passed inline
to Code Mode, and the exact shape of a failure. All of this is listed,
prominently, in `references/mcp-mechanism.md` and at the top of
`scripts/deploy.py` itself — verify each item against a live, configured
connector (Code Mode's `get_tool_output_schema` helps here) before
trusting this in production.

## Invocation contract

```
Skill(uab-deploy, args: "--repo-url=https://github.com/org/repo.git
  --target-branch=main --source-dir=/workspace/my-app")
```

- `--repo-url=<https-url>` (**required**) — the target repo's URL. Owner
  and repo name are parsed from its path (works for `github.com` or a
  GitHub Enterprise host — the connector, not this parsing step,
  determines which host is actually addressed).
- `--target-branch=<name>` (**required**) — the branch this code should
  eventually live on (e.g. `main`, `develop`). This skill does **not**
  push directly onto it — see "Branch strategy" below. It's the base the
  deploy branch is created from, and the branch reported back as the
  eventual merge target.
- `--source-dir=<path>` (**required**) — absolute path to the generated
  app's root, already on disk in this sandbox. Nothing is re-downloaded
  or re-unzipped.
- `--mcp-server-name=<name>` (optional, default `github`) — the name this
  GitHub MCP connector was given in TrueForge's `Settings → Connectors`.
- `--app-name=<slug>` (optional, default: derived from `--source-dir`'s
  folder name) — used to derive the deploy branch name and default
  commit message.
- `--deploy-branch-name=<name>` (optional, default `deploy/<app-slug>`).
- `--target-subdir=<path>` (optional, default: repo root) — use this when
  the target repo already holds other projects/content, so the generated
  app lands in its own subfolder instead of the repo root.
- `--commit-message=<text>` (optional, default: `Deploy <app-name> from
  generation sandbox`).
- `--repo-visibility=<private|public>` (optional, default `private`) —
  only used if the repo doesn't already exist and this run creates it.
- `--qa-status=<passed|failed|skipped|unknown>` (optional, default
  `unknown`) — **informational only**, echoed in the report. See
  "Relationship to QA" below — it never gates whether the push happens.

## Deploy flow

Work through these steps in order, every time, via `scripts/deploy.py`
(see "Mandated script" below) — never by hand.

**a. Validate arguments.** `--repo-url` parses to an owner/repo,
`--source-dir` exists and looks like a generated app root (`PLAN.md`,
`package.json`, or `requirements.txt`/`pyproject.toml` present). Fail
loudly and stop before any MCP call on anything missing or malformed.

**b. Ensure the repo exists.** Call the connector's repo-creation tool
with `auto_init` so a brand-new repo has an initial commit to branch
from. Treat "already exists" as success, not failure, and continue.

**c. Resolve `--target-branch`'s tip commit.** If the repo was just
created and its actual default branch name doesn't match
`--target-branch` (GitHub defaults new repos to `main`; the caller may
have asked for `develop`), create `--target-branch` from the default
branch's tip first — never silently substitute one branch for the other.

**d. Determine the deploy branch.** `--deploy-branch-name` if given,
else `deploy/<app-slug>`. Look it up: already exists → this is a re-run
for this app (reuse it). Otherwise → create it from `--target-branch`'s
tip (first deploy for this app).

**e. Collect the generated app's files.** Walk `--source-dir`, excluding
exactly the categories `uab-app-creator-nobrand`'s `package-app-fast.sh`
already excludes: `node_modules/`, `.next/`, `.venv/`, `__pycache__/`,
`.data/`, `.localstorage/`, `.git/`, `.verify/`, `.env`, `.env.local`.
(`.gitignore` itself is a normal file and IS collected — only the `.git/`
directory is excluded.)

**f. Push as a single commit.** One call to the connector's push tool
with every collected file, targeting the deploy branch. This is
inherently additive/overwrite-only for the paths given — never deletes
or mirror-prunes anything else already in the target repo.

**g. Report back.** See "Report back" below.

## Mandated script — never hand-roll individual MCP calls

Always run `scripts/deploy.py` for steps b–f above, via Code Mode, exactly
once per invocation — never issue `call_tool` invocations by hand, even
for a case that looks simple. It's what enforces every guardrail in this
file the same way every run: the deploy-branch rule is applied
consistently, the file-collection exclude list can't silently drift, and
error handling is consistent. Same reasoning `uab-app-creator-nobrand`'s
"never zip the app folder any other way" rule already establishes for
packaging.

Run it to completion synchronously — don't background this the way
`uab-app-qa`'s install/build steps use `bg-run.sh`/`bg-status.sh`. Those
exist because there's plenty of time later to poll; `uab-deploy` runs at
the very end of the sandbox's life, so there's no guarantee a poll loop
has time left to complete before teardown.

## Branch strategy

Full reasoning in `references/branch-and-commit-strategy.md`. Summary:
**always push to a dedicated `deploy/<app-slug>` branch, never directly
to the literal `--target-branch` named by the caller — and reuse that
same branch across re-runs of the same app, appending a new commit each
time.** The push mechanism (a commit-creation tool call, not a raw ref
update) has no force-push-shaped operation at all on this path — the
class of bug a git-based design would have to explicitly forbid is
structurally absent here, not just prohibited by convention.

## Relationship to QA

`--qa-status` is accepted and echoed in the report, but it never gates
or alters the push — `uab-deploy` has no way to independently verify a
caller-supplied `--qa-status=passed` claim (`uab-app-qa` never calls into
this skill; see "Ownership" above), so trusting the flag as a real gate
would be false confidence dressed up as a check. The orchestrating
process already has a genuinely robust gate available to it: **don't
invoke `uab-deploy` at all** until QA has actually passed, or until a
human has explicitly decided an unverified push is acceptable. That
keeps this skill single-purpose, and keeps the one real safety mechanism
— whether to invoke it at all — where it actually has teeth.

## Hard rules

- Never fabricate or guess a repo/branch's existence — always resolve it
  via a real tool call before deciding to create vs. reuse.
- Never push directly to the literal `--target-branch` — always the
  derived/overridden `deploy/...` branch.
- Never attempt to widen the GitHub connector's permissions or work
  around a permission/scope error — report it plainly instead.
- Never skip or drift the file-collection exclude list from
  `package-app-fast.sh`'s list.
- Never be invoked from inside `uab-app-creator-nobrand`,
  `uab-app-builder`, `uab-branding`, or `uab-app-qa`'s own instructions.
- Never write Azure Bicep, `azure.yaml`, pipeline files, or take any
  non-git deployment/hosting action.
- Never hand-roll individual `call_tool` invocations outside
  `scripts/deploy.py`.

## Report back

Full templates in `references/report-template.md`.

**On success:** one sentence on what got pushed; the repo and the
*actual* branch pushed, stated plainly as a deploy branch (with a
one-line reminder that merging into `--target-branch` is a separate
step); whether this was the first push for this app or an update to an
existing deploy branch; whether a new repo had to be created (say this
plainly — it's a bigger action than a normal push); the `--qa-status`
value as given, with an explicit "not confirmed to build/run/pass QA in
a real environment" caveat whenever it isn't `passed` — say this
plainly, not buried, the same register `uab-app-creator-nobrand` uses
for "the output is unverified"; and a closing line that nothing beyond
this happened (no hosting, no pipeline, no other infrastructure).

**On failure:** state plainly that the push did not succeed and exactly
how far it got; the plain-language failure category (connector not
configured, permission/scope, branch diverged) and one concrete next
step; and explicit confirmation that nothing destructive was attempted
and the target repo's real branches are untouched.

## For IT / DevOps — Deploying this app

This app follows UAB's standard three-branch process: `develop` → `qa` →
`production`. Development and Production are two completely separate
deployments with their own resources — nothing (data, files, uploads) is
shared between them. QA is not a deployed environment at all; it exists
only to build and smoke-test a pull request before it's allowed to merge
toward production.

### How deployment works
1. **Push to `develop`** → `azure-pipelines-dev.yml` installs azd,
   authenticates, and runs `azd up` against the Development environment
   immediately — no approval gate. This is where day-to-day changes land
   first.
2. **Open a pull request into `qa`** (or push directly to `qa`) →
   `azure-pipelines-qa.yml` installs dependencies, builds the app the same
   way the Dockerfile does, starts it, and checks the health endpoint. It
   never touches Azure and never deploys anything — a failure here just
   blocks the pull request.
3. **Open a pull request into `production`** → the same QA pipeline runs
   again as the required check before merge is allowed.
4. **Push to `production`** (typically the result of merging that approved
   pull request) → `azure-pipelines-prod.yml` installs azd, authenticates,
   waits for the manual approval configured above, then runs `azd up`
   against the Production environment.

In both Dev and Prod, `azd up`:
   - Provisions a Resource Group, Container Registry, Key Vault, Application
     Insights, and Container Apps environment on first run for that
     environment
   - Builds the Docker image and pushes it to the registry
   - Deploys the container to Azure Container Apps
   - Outputs the live URL in the pipeline logs

Subsequent runs re-run `azd up`, which skips already-provisioned resources
for that environment and only updates the running container image.

**Rolling back:** each deploy creates a new Container Apps revision. To roll
back, activate the previous revision in the Azure portal (Container App →
Revisions) — no pipeline run needed. (Note: a full infrastructure
re-provision briefly resets the app to a placeholder hello-world image until
the deploy step replaces it — normal azd behavior.)

### Monitoring
Application Insights and an external availability test are provisioned
automatically for both Development and Production — no setup needed. The
availability test pings the health endpoint from outside; if it stops
responding, an alert email goes to the project contact (`<Q11 name/email>`).
Note: request/error telemetry from inside the app itself is NOT collected
yet — the scaffold doesn't include an Application Insights SDK. To add
in-app telemetry later, install the `applicationinsights` npm package (or
`azure-monitor-opentelemetry` for Python); a TODO stub in the code marks the
place.

### Local development
1. `.env.local` is already generated (gitignored, never committed) with
   everything you can fill in locally. If this app has a login, the Hydra
   values are already real and working — no setup needed. For a data store,
   the zero-config local fallback works with nothing filled in; only add a
   value there if you deliberately want to test against the real Azure
   resource instead (note: the database password rotates on every deploy —
   re-copy DATABASE_URL from Key Vault after each deployment). For an external system integration, add a real test
   credential there if you want to test that integration locally — leave it
   blank to skip. Never put a real value in `.env.template` — it's committed
   to this repo and documents variable names only.
2. Install dependencies: `npm install` (or `pip install -r requirements.txt`)
3. Run locally: `npm run dev` (or `uvicorn app.main:app --reload`)
4. Health check: http://localhost:3000/api/health

### Fonts
This app uses the UAB brand fonts `kulturista-web` and `proxima-nova` via

`<head>` in `src/app/layout.tsx` — the TODO comment marks the exact location.

### Decommissioning this app
Both environments need to be torn down separately — running `azd down --purge`
tears down only the environment selected at the time (Resource Group,
Container Registry, Key Vault, Application Insights, Container Apps, and any
database/storage for that environment). Use `--purge`: Key Vault has
soft-delete, and without purging, re-creating an environment with the same
name later fails on the Key Vault name until the soft-deleted vault is
manually purged. Run it once for `<app-name>-dev` and
once for `<app-name>-prod`. Do this when the app is no longer needed — an
unused app left running still costs money and counts against
`<Q11 department/cost center>`'s budget.
